# Non-Skill Decision Tree

如果它只是一次性请求，就不要做成 skill。

如果它会反复出现，并且规则相对稳定，就值得做成 skill。

如果它需要大量实时判断但没有固定流程，优先保留成普通对话步骤。

## Three Gates（前置三问，全部通过才继续设计）

任何一问为否，停止：

1. **模型已经能做好这件事吗？** 能 → skill 是多余开销。
2. **用户会用它 5 次以上吗？** 一次性自动化 → 直接 prompt 或一次性脚本。
3. **这件事真的超出模型内置能力吗？** 给模型已懂的事情加指令，每次触发都浪费 context。

理由：这三问过滤掉绝大多数「要不要做 skill」的冲动。三问全过，才是真 skill。

同一组三问反向用于审计已有 skill（德鲁克三查）：

| # | 问题 | 答案为否 |
|---|------|---------|
| 1 | 没有这个 skill，结果会变差吗？ | 该删，不改 |
| 2 | 用户会用它 5 次以上吗？ | 一次性任务，不值得优化 |
| 3 | 模型自己能做吗？ | 不需要 skill |

细节与边界情形：`references/methodology.md` 第 1 节。
