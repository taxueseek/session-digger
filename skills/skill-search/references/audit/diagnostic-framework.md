# Skill 诊断方法论 v3.0

> 融合逐层消解漏斗 + 分类路由 + agent/CLI 环境特性。
> 核心转变：从「平铺检查项」变成「逐层消解 + 分类路由 + 原子修复」。

---

## 核心哲学

**维特根斯坦**：语言混乱的地方，思维一定混乱。触发词模糊 = 路由混乱。
**奥派经济学**：激励决定行为。token 是 skill 生态的「价格信号」，浪费 token = 价格失灵。
**阿德勒心理学**：问题本身往往是错的。先验证 skill 该不该存在，再验证它做得好不好。

## Phase 0：前置审查（德鲁克三问）

拿到一个 skill 改进请求前，先问三问。任何一问答案为否，停止诊断。

| # | 问题 | 消解结果 |
|---|------|---------|
| 1 | **没有这个 skill，结果会变差吗？** | 不会 → 该删，不改 |
| 2 | **用户会用它 5 次以上吗？** | 一次性任务 → 不需要优化 |
| 3 | **模型自己能做吗？** | 能 → 不需要 skill |

三问全通过 → 进入 Phase 1。

## Phase 1：消解漏斗（5 层逐层过关）

每层发现问题就停止，不进入下一层。

### 第 1 层：需求真实性检测

**问法**：这个 skill 解决的是真实需求，还是某个更大问题的替代方案？有没有同功能 skill 可复用/合并？

**强制工具（prior-art）**：用 name + description 意图跑一次 prior-art（`scripts/research_prior_art.py`，四外部通道 + 本地引擎）。只吸收结构化报告，不读原始会话；不依赖外部全量引擎。

```bash
python3 scripts/research_prior_art.py "<意图>" --name <skill-name> --local --digger --summary
# 快速：省略 --local --digger    完整：默认开外部目录
```

| Seek 信号 | 漏斗动作 |
|-----------|----------|
| `reuse`/`adapt` 且 TARGET 是**其他** skill | 倾向消解：合并/删除本 skill（删除须用户确认） |
| `build` + 无覆盖 usage | 倾向通过：真实缺口 |
| `missing_evidence` | 通过但降级：写明未完备检索 |
| 用户要求跳过 Seek | 允许，报告写 `SEEK_ACTION: skipped` |

**其他信号**：
- 用户说「帮我优化这个 skill」→ 可能是「我用不好这个 skill」→ 真正的问题是触发机制或文档
- skill 的存在是为了弥补另一个 skill 的缺陷 → 应该修根源，不该加补丁
- skill 从未被触发过（usage / digger）→ 可能是幻觉需求

**如果检测到**：
> 这个 skill 可能是「{真实需求}」的替代品。直接解决那个问题，比优化这个 skill 更有效。

→ 需求不真实 → 建议删除或合并，流程结束
→ 需求真实 → 继续第 2 层

### 第 2 层：触发词精确度检测

**问法**：description 中的触发词是否正确定义？有没有模糊词？

**常见陷阱词**：「各种」「相关」「帮助」「处理」「支持」「管理」

**检测法**：
1. 删掉 description 里的触发词，skill 还能触发吗？能 → 触发词没用
2. 触发词和其他 skill 碰撞吗？碰撞 → 路由混乱
3. description 是当「分类器 prompt」写还是当「文档」写？→ 文档式 description 导致误触发

**如果检测到**：
> description 里的「{词}」没有精确定义。它可以指 A，也可以指 B。用户说 X 时，你无法确定该不该触发这个 skill。

→ 用户给出精确定义 → 重写 description，继续第 3 层
→ 用户给不出 → 触发机制需要重新设计

### 第 3 层：前提假设审查

**问法**：这个 skill 存在的前提假设成立吗？

**常见前提假设**：
- 「用户已经知道 X」→ 验证：用户真的知道吗？
- 「这个功能模型原生做不到」→ 验证：真的做不到吗？
- 「用户会按这个顺序操作」→ 验证：实际使用顺序是什么？
- 「这个 skill 的调用者具备 Y 权限/工具」→ 验证：前置依赖满足吗？

**如果检测到**：
> 这个 skill 假设了「{假设}」。但这个假设可能不成立：{原因}。如果假设不成立，这个 skill 的存在基础就动摇了。

→ 假设被推翻 → 需要重新设计 skill 的定位
→ 假设成立 → 继续第 4 层

### 第 4 层：主要矛盾识别

**问法**：用户报告的多个问题中，哪个解决了其他的会自动好转？

**检测法**：
- 列出所有发现的问题
- 问：哪个问题是其他问题的前提？
- 解决根因问题后，多少表面问题会自行消失？

**如果找到**：
> 你发现了 {N} 个问题，但核心只有一个：{主要矛盾}。
> 解决这个，其他 {M} 个问题会自行缓解。我们只解决这一个。

→ 找到主要矛盾 → 收窄诊断范围，继续第 5 层
→ 问题不可拆 → 继续第 5 层

### 第 5 层：有效性审查

**问法**：这个 skill 值得存在吗？值得现在改吗？

**德鲁克三查**：
- 改进这个 skill，对谁有价值？是用户确认的，还是自认为的？
- 如果不改，会怎样？如果答案是「也没什么大不了的」——不值得投入
- 是在做对的事，还是在把事做对？有效性先于效率

→ 值得做 → 漏斗通过，进入 Phase 2
→ 不值得做 → 建议用户把精力放在别处

## Phase 2：问题分类 → 选择诊断模式

漏斗通过后，对 skill 问题进行分类，选择对应诊断深度：

### 分类 A：功能性缺陷（快速扫描模式）

**特征**：skill 无法正常工作——断链、版本不一致、硬编码路径、备份残留

**诊断深度**：快速扫描（只查 P0 项）
**输出**：问题清单 + 直接修复
**参考**：engineering-patterns.md 模式 1/2/8/9

### 分类 B：效率问题（量化分析模式）

**特征**：skill 能用但太慢/太臃肿——token 浪费、重复内容、必读加载过多

**诊断深度**：量化分析（token 统计 + 效率报告）
**输出**：量化报告 + 优化方案
**参考**：engineering-patterns.md 模式 3/4/5/10

### 分类 C：架构问题（深度诊断模式）

**特征**：skill 结构有问题——职责重叠、边界模糊、缺少路由、注册副本不一致

**诊断深度**：完整分析（结构扫描 + 边界测试 + 一致性检查）
**输出**：架构改进方案
**参考**：engineering-patterns.md 模式 6/7 + design-patterns.md

### 分类 D：触发机制问题（分类器校准模式）

**特征**：skill 该触发时不触发，不该触发时误触发

**诊断深度**：description 作为分类器 prompt 的校准测试
**输出**：触发词优化方案 + 边界测试结果
**参考**：anti-patterns.md 反模式 1/2/3/14

### 路由决策树

```
skill 问题
  → 能用吗？
    → 不能 → 分类 A（快速扫描）
    → 能用但慢/臃肿 → 分类 B（量化分析）
    → 能用但结构乱 → 分类 C（深度诊断）
    → 触发不对 → 分类 D（分类器校准）
    → 混合问题 → 先 A 再 B/C/D（功能性优先）
```

## Phase 3：诊断原子操作清单

每种问题类型对应的具体检测 + 修复操作。替代原来的 P0/P1/P2 平铺。

### A 类：功能性缺陷

| 检测项 | 检测命令 | 修复操作 | 参考模式 |
|--------|---------|---------|---------|
| **断链引用** | `grep -oP 'references/[^ )\]]+' SKILL.md \| while read f; do [ ! -f "$f" ] && echo "断链: $f"; done` | 修正路径或删除引用 | 模式1 |
| **版本号不一致** | `grep -ri "version" SKILL.md scripts/*.{py,sh}` | 以脚本版本为基准统一 | 模式2 |
| **硬编码路径** | `grep -rn "~/.agents/\|~/.claude/" scripts/` | 改为动态发现 | 模式9 |
| **备份残留** | `ls -d *.bak/ 2>/dev/null` | 移到 `.archive/` | 模式8 |
| **注册副本缺失** | 检查全局注册目录与真源是否一致 | 同步或创建符号链接 | 模式7 |

### B 类：效率问题

| 检测项 | 检测命令/方法 | 修复操作 | 参考模式 |
|--------|-------------|---------|---------|
| **SKILL.md 体量** | `wc -l SKILL.md` → >80 行需瘦身 | 规则下沉到 references/，路由表精确引用 | 模式3 |
| **必读文档** | 检查路由表中标注"必读"的条目 | 改为按操作路由精确引用 | 模式4 |
| **重复内容** | `diff --side-by-side file1 file2 \| grep "\|"` | 提取为单一引用源 | 模式5 |
| **CLI 冗余调用** | 分析工作流中重复的 CLI 命令 | 合并或缓存 | 模式10 |
| **token 噪音比** | 统计一次典型触发的 token 开销，按「必要/可选/冗余」分类 | 优先削减冗余 | 模式3+4 |

### C 类：架构问题

| 检测项 | 检测命令/方法 | 修复操作 | 参考模式 |
|--------|-------------|---------|---------|
| **DO NOT use when 缺失** | 检查 SKILL.md 是否有边界声明 | 补充 3-5 条边界 | 模式6 |
| **职责重叠** | 找相邻 skill 对比 description 和功能 | 明确分工 + 交叉引用 | — |
| **膨胀 Body** | `wc -l SKILL.md` → >500 行 | 把参考信息移到 references/ | 模式3 |
| **工作流结构** | 判断 skill 是线性/并行/探索型 | 选择匹配的 design-pattern | design-patterns.md |

### D 类：触发机制问题

| 检测项 | 检测命令/方法 | 修复操作 | 参考 |
|--------|-------------|---------|------|
| **触发词碰撞** | 对比相邻 skill 的 description | 互斥化触发词 | anti-patterns #2 |
| **模糊触发** | description 是否含「各种」「相关」等 | 用具体动词+具体对象替换 | anti-patterns #1 |
| **术语触发** | 触发词是否用户会说的话 | 用用户原话替换 | anti-patterns #3 |
| **description 类型** | 当分类器 prompt 测试：给 10 个请求，看路由是否正确 | 重写为分类器格式 | quality-checklist L1 |
| **模式错位** | 用户是模糊想法还是已有解法 | 模糊想法先走 Evaluate | anti-patterns #14 |

## Phase 4：诊断报告模板

量化 + 结构化。替代原来的平铺表格。

```markdown
# Skill 诊断报告：<skill-name> v<version>

## 消解漏斗结果
- 第 1 层（需求真实性）：✅ 通过 / ❌ 消解 — {原因}
  - SEEK_ACTION: {reuse|adapt|build}
  - SEEK_TARGET: {path|name|url|-}
  - SEEK_EVIDENCE: {validated|hypothesis|missing_evidence|-}
- 第 2 层（触发词精确度）：✅ 通过 / ❌ 消解 — {原因}
- 第 3 层（前提假设）：✅ 通过 / ❌ 消解 — {原因}
- 第 4 层（主要矛盾）：{识别出的主要矛盾}
- 第 5 层（有效性）：✅ 值得改 / ❌ 不值得
```

## Skill 问题分类体系

替代原来的 P0/P1/P2 平铺。新的分类按「问题性质」而非「严重度」组织。

### 按问题性质分类（一级）

| 分类 | 含义 | 对应 Phase | 诊断深度 |
|------|------|-----------|---------|
| **A — 功能性缺陷** | skill 无法正常工作 | Phase 3 A 类 | 快速扫描 |
| **B — 效率问题** | skill 能用但有浪费 | Phase 3 B 类 | 量化分析 |
| **C — 架构问题** | skill 结构/边界有缺陷 | Phase 3 C 类 | 深度诊断 |
| **D — 触发机制问题** | 该触发时不触发，不该触发时误触发 | Phase 3 D 类 | 分类器校准 |

### 按严重度分类（二级，在每个一级分类内）

| 级别 | 含义 | 处理方式 |
|------|------|---------|
| **P0** | 阻断性问题（skill 无法使用或结果错误） | 立即修 |
| **P1** | 显著影响（每次触发都有感知） | 本次修 |
| **P2** | 优化项（改了更好，不改也行） | 有空再修 |

### 组合示例

- `A-P0`：断链引用（功能性缺陷 + 阻断性）→ 立即修，用模式1
- `B-P1`：SKILL.md 超 80 行（效率问题 + 显著影响）→ 本次修，用模式3
- `C-P2`：DO NOT use when 缺失（架构问题 + 优化项）→ 有空修，用模式6
- `D-P1`：触发词碰撞（触发机制 + 显著影响）→ 本次修，重写 description

## Agent/CLI 环境特有检查项

当前框架缺少的维度，专门补充。

### E 层：Skill 加载体系

| 检查项 | 说明 |
|--------|------|
| **三层加载完整性** | metadata（frontmatter）→ body（SKILL.md 正文）→ references/（按需加载）。三层都有且分工明确吗？ |
| **真源与注册副本一致性** | 项目真源与全局注册目录是否同步？推荐用符号链接或同步脚本。 |
| **Description 作为分类器** | description 不是文档，是 LLM 的分类器 prompt。测试方法：给 10 个请求，看路由是否正确。 |

### F 层：Token 消耗模型

| 检查项 | 说明 |
|--------|------|
| **典型触发开销** | 一次触发加载多少 token？分层统计：frontmatter + body + 必读 references |
| **噪音比** | 加载的 token 中，实际被使用的比例是多少？< 50% 说明有显著浪费 |
| **按需加载率** | references/ 文件是否按需读取？还是全量加载？ |

## 迭代触发

- 连续 3 次诊断发现同类问题 → 将修复模式加入 engineering-patterns.md
- 新增反模式 → 更新 anti-patterns.md + quality-checklist.md
- Token 基线变化 >20% → 重新校准 Token 效率报告
- 自身版本升级 → 执行自诊断（Phase 0 目标设为自身路径）
