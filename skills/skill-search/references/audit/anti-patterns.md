# Skill 反模式清单

构建或审查 skill 时对照。发现一条就修，不要等到发布后。

---

## 14 条反模式

### 触发层面

**1. 模糊触发**
症状：description 写「帮助用户处理各种任务」
修法：用具体动词 + 具体对象。「写小红书标题」「诊断简历问题」

**2. 触发词碰撞**
症状：多个 skill 的 description 用同样的触发词
修法：每个 skill 的触发词互斥。用「Use other skills for」划清边界

**3. 术语触发**
症状：用专业术语做触发词，但用户不会这样说
修法：用用户的原话。「帮我写个东西」而不是「内容创作」

### 结构层面

**4. 膨胀 Body**
症状：SKILL.md 超过 500 行，塞满了参考信息
修法：把参考信息移到 references/，body 只留执行指令

**5. 纯文本指导**
症状：全是「你应该这样做」，没有可执行的命令或代码
修法：加可执行代码块。可执行指令显著提升执行准确率

**6. Fortune Cookie 指导**
症状：「注意质量」「保持专业」——说了等于没说
修法：改成可验收的标准。「输出包含3个具体案例，每个案例有真实数据」

### 逻辑层面

**7. 什么都想做**
症状：一个 skill 里有两套独立流程，或者子目录互相引用
修法：拆分。一个 skill 只做一件事

**8. 隐藏假设**
症状：假设用户已经知道某个前置知识或工具
修法：在输入部分明确列出前置条件

**9. 无验收标准**
症状：没有说「什么叫做好了」
修法：补交付标准，可验收、可描述

**10. 无迭代触发**
症状：没有说「什么时候该更新这个 skill」
修法：补迭代触发条件

**11. 幻觉 skill**
症状：身体里的每条规则都「看起来对」，但没有一个来自真实场景。声称能解决一个问题，但说不清「不做这条指令，Agent 会在什么具体情况下犯错」
修法：每条指令必须能追溯到真实失败案例。写不出这条指令对应的失败场景——说明这条指令可能不需要

**12. 完成幻觉**
症状：写完就说「完成了」，没有真实场景验证过。交付标准写着「高质量输出」但说不清什么叫高质量
修法：至少跑 3 个真实请求，确认输出符合预期。交付标准必须可验收——第三方看了能判断是否达标

### 路由层面

**13. 菜单式路由**
症状：用户说「帮我弄个 skill」，你列 4 个选项让他选
修法：听懂了就直接走。只在不确定时才问一个问题确认

**14. 模式错位**
症状：用户手里是模糊想法，但跑了完整六步编译——做出来的不是他想要的
修法：先判断「已有解法」还是「模糊想法」。模糊想法先走 Evaluate，搞清楚边界再动手

## 快速检查法

拿到一个 skill，用这三个问题快速过滤：

1. **删掉 description 里的触发词，skill 还能触发吗？** 能 → 触发词没用，重写
2. **把 body 里的规则全删掉，只留例子，Agent 能做对吗？** 能 → 规则多余，删掉
3. **把这个 skill 给一个从没见过它的人，他能用吗？** 不能 → 缺上下文，补上
